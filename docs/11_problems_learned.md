# Проблемы и решения: опыт из коммитов

## 1. Stale Trend Alerts on Cold Start Burst

**Проблема**: при перезапуске collector догонял тысячи пропущенных сообщений. TrendTracker сразу кластеризовал их и.fire() алерты для трендов, которые были hot НЕДЕЛЮ назад.

**Решение**: добавили `alerted_at` в trends table. При старте проверяется `is_fresh = (now - cluster.last_seen) < 2 hours`. Alert.fire() только если свежий AND never alerted.

```python
is_fresh = (datetime.now(timezone.utc) - cluster.last_seen).total_seconds() < 7200
if cluster.unique_sources >= min_sources and not alerted_at_val and is_fresh:
    ...fire alert...
```

## 2. Duplicate Trend Detection (Message Overlap)

**Проблема**: HDBSCAN с `cluster_selection_epsilon` мог разбить один тренд на 2 кластера. Или при перезапуске тот же тренд создавался заново с другим именем.

**Коммит**: `feat: deduplicate trends by message overlap, make hdbscan_epsilon configurable`

**Три уровня мержинга**:
1. Exact topic name match (within 24h) — быстрое совпадение
2. ChromaDB semantic similarity — если топик изменился но содержимое похоже
3. Message overlap ≥ 2 — если все предыдущие методы не сработали

## 3. Hot Trend URL Rendering

**Проблема**: private channels (числовой ID) генерировали некорректные ссылки. Telegram использует формат `t.me/c/{chat_id}/{msg_id}` для приватных каналов.

**Коммит**: `fix: format numeric private channel ids correctly as t.me/c/id URLs`

```python
def post_url(row):
    ext_id = row.get("external_id", "")
    src    = row.get("source_name", "")
    if ext_id and src.replace("-", "").isdigit():
        # -100123456789 → 123456789
        clean = src.replace("-100", "").replace("-", "")
        return f"https://t.me/c/{clean}/{ext_id}"
```

## 6. ChromaDB Collection Loss on Restart

**Проблема**: если ChromaDB контейнер перезапускался (OOM, crash), collection "news_radar" исчезала. Все subsequent upsert-ы падали.

**Решение**: `_reconnect_if_collection_lost()` — при ошибке "Collection does not exist" делается force reconnect + retry once.

```python
def _reconnect_if_collection_lost(self, e):
    if "does not exist" in str(e) or "404" in str(e):
        self._connect(force=True)
        return True
```

## 9. SQLite WAL Lock (Concurrent Writers)

**Проблема**: collector пишет в messages, analyzer одновременно делает commit. "database is locked" при одновременном доступе.

**Решения (накопленные)**:

- `check_same_thread=False` — разрешён multi-threaded access

## 13. Telegram Bot Parse Mode Fallback

**Проблема**: digest с HTML parse_mode падал при отправке (Telegram API error). Пользователь видел пустоту.

**Решение**: fallback на plain text:

```python
try:
    await update.message.reply_text(content, parse_mode=parse_mode)
except Exception as e:
    # Strip HTML tags → plain text
    plain = re.sub(r"<[^>]+>", "", content)
    plain = plain.replace("*", "").replace("_", "")
    await update.message.reply_text(plain)
```

Никогда не отправлять ошибку пользователю — только fallback контент.

## 14. Client-Side-Only Threshold Starves Low-Traffic Search Queries

**Проблема** (ТЗ #4 И2 приёмка): `HackerNewsCollector` запрашивал Algolia `search_by_date` без параметров и фильтровал `points >= min_points` уже на клиенте. `search_by_date` без фильтров отдаёт просто N самых свежих историй — у низкотрафикных запросов («ai agents») почти все свежие истории ещё не набрали очков. Живой замер: 1 из 20 хитов проходил порог `min_points=30`.

**Решение**: порог и окно по возрасту — в сам запрос (`numericFilters=points>={min},created_at_i>{cutoff}`), клиентский фильтр остаётся только страховкой на случай, если параметр запроса не сработал:

```python
params={
    "query": query, "tags": "story", "hitsPerPage": hits_per_page,
    "numericFilters": f"points>={min_points},created_at_i>{cutoff_epoch}",
}
```

Общий урок: если апстрим API поддерживает серверную фильтрацию — не эмулировать её клиентским `if`, иначе бюджет (страница результатов, rate limit) тратится на то, что всё равно будет выброшено.

## 15. Shared Fetch Budget Needs a Per-Feed Cap, Not Just a Per-Cycle One

**Проблема** (ТЗ #4 И2 приёмка): у `FullTextFetcher` был только общий `max_fetches_per_cycle`. Фиды обходятся по порядку — первый фид в списке (`openai.com`, отвечающий 403 на любой UA) впустую съедал весь лимit цикла, до остальных фидов очередь не доходила: HuggingFace получал 0 статей, хотя сам сайт отдавал 200 и `trafilatura` бы справилась.

**Решение**: два независимых лимита — общий `max_fetches_per_cycle` и по-фидовый `max_fetches_per_feed` (ключ `feed_key` — URL фида или HN-запрос), плюс предохранитель по домену: после первого 401/403 домен блокируется до конца цикла, не тратя лимит на заведомо безнадёжные повторы. Общий урок: общий лимит на несколько независимых источников без резервирования per-source — типичный источник starvation, когда порядок обхода определяет, кому вообще достанется бюджет.

## 16. Tracking Params in URLs Defeat URL-Based Dedup

**Проблема** (ТЗ #4 И2 приёмка): Habr кладёт в ссылку `?utm_campaign=...&utm_source=...&utm_medium=rss`. Дедуп по URL (частичный уникальный индекс из И1) сравнивает строки буквально — та же статья с разными UTM-хвостами (например, если её же принесёт другой агрегатор) не схлопнется.

**Решение**: `collectors/url_utils.py::normalize_url()` — срезает `utm_*`/`fbclid`/similar, фрагмент и хвостовой `/`, применяется **до** любой проверки dedup и до сохранения (иначе поле `url` в БД останется «грязным», и уже сохранённые записи не подтянутся под новый нормализатор без бэкфилла).

## 17. Порог, померенный по разметке, а не по тексту, молча не срабатывает

**Проблема** (ТЗ #4 И3): в `rss.py` порог «короткий сниппет → догрузить полный текст» (`_MIN_SNIPPET_CHARS_FOR_FULL_FETCH = 500`) сравнивался с длиной `entry.summary` **как есть**, а Хабр, dev.to и Simon Willison кладут туда сырой HTML. Короткий тизер, обёрнутый в `<p>` и восемь `<img src="...">`, легко перешагивает 500 символов одной разметкой — и догрузка не происходит никогда. Тот же HTML при этом уезжал в `messages.text` и попал бы в промпт классификатора дословно.

**Решение**: чистить сниппет до сравнения, сравнивать длину очищенного текста, его же и сохранять:

```python
raw_snippet = (entry.get("summary") or "").strip()
snippet = _clean_snippet_html(raw_snippet)
if len(snippet) < _MIN_SNIPPET_CHARS_FOR_FULL_FETCH:
    ...
```

Общий урок: порог имеет смысл только вместе с ответом на вопрос «длина **чего**». Если между источником и порогом есть слой представления (разметка, экранирование, base64), метрика меряет его, а не содержимое — и отказ тихий: система просто перестаёт срабатывать, ничего не логируя.

Второй урок из того же места: `trafilatura` рассчитана на целые документы и на коротком фрагменте штатно возвращает `None`. Библиотека, применённая вне своего сценария, не обязана падать — она обязана вернуть что-то бесполезное. Нужен детерминированный фоллбэк, а не надежда.

## 18. Ключ конфига без потребителя — это конфиг-ложь

**Проблема** (ТЗ #4 И3): спека (р. 8.1) предписывала поставить `sources.telegram.enabled = false`, чтобы поставить крипту на паузу. Но читать этот ключ было некому: `poll_runner` гатит только `rss` и `hackernews`, а telegram-коллектор — отдельный compose-сервис `collector` с `restart: unless-stopped`, который стартует и собирает безусловно. Добавь ключ как есть — в `settings.json` стоит `false`, в логах тишина, а крипта продолжает литься в базу.

**Решение**: провести флаг по-настоящему — `_is_telegram_enabled()` и гейт в начале `main()`, до чтения `TELEGRAM_*` из окружения (выключенному деплою credentials не нужны). Сервис при этом **идлит, а не выходит**: с `restart: unless-stopped` выход превращается в рестарт-луп.

Общий урок: правило «каждый ключ — в `DEFAULT_CONFIG` и в `settings.json`» описывает, как ключ **доедет** до кода, но ничего не говорит о том, что кто-то его **прочитает**. Прежде чем заводить переключатель — найти строчку, которая на него смотрит; если её нет, написать её в том же коммите. Иначе получается галочка, которая ничего не выключает, а это хуже, чем её отсутствие: она врёт.

Сопутствующая грабля — глубина слияния. `ConfigWatcher._load()` копирует значения по ключам **верхнего уровня**: если `settings.json` определяет `sources`, он определяет его целиком, и подключи из `DEFAULT_CONFIG` не подмешиваются. Поэтому вложенный ключ читается с дефолтом на месте чтения — `sources.get("telegram", {}).get("enabled", True)` — а не в расчёте на `DEFAULT_CONFIG`.

## 19. Гит-локи остаются навсегда там, где агенту запрещено удалять файлы

**Проблема** (21.09): владелец не мог закоммитить — `fatal: Unable to create '.git/index.lock': File exists`. В `.git/` лежали нулевые `index.lock` и `HEAD.lock`, а рядом `index.lock.stale-20260918` — след той же истории неделей раньше, когда лок не удалили, а переименовали.

Причина не в гите. Папка проекта монтируется в среду ИИ-исполнителя так, что **запись и переименование разрешены, а удаление — нет** (`rm` → `Operation not permitted`). Гит берёт лок и снимает его двумя разными способами: при успешной записи — `rename(index.lock, index)`, который проходит, а при откате (прерванная команда, `git status`, не изменивший индекс) — `unlink`, который не проходит. Любая операция, откатывающая лок, оставляет нулевой файл навсегда, и дальше **любой** коммит, в том числе из обычного терминала владельца, упирается в него.

**Решение**: снести `.git/*.lock` (убедившись, что ни один гит-процесс не работает), затем `git fsck --connectivity-only` для проверки. Не переименовывать в `*.stale-*` — переименованный лок не мешает гиту, но копится и путает следующего.

Общий урок: среда, где разрешено создавать файлы и запрещено удалять, ломает любой протокол на lock-файлах — они по определению рассчитаны на снятие. Симптом проявляется не там, где возник: агент отработал и ушёл, а спотыкается владелец в своём терминале через час. Если среда исполнителя такая — снятие локов должно быть явным шагом, а не побочным эффектом.

Второе, из того же разбора: у гита в среде исполнителя не было `user.name`/`user.email`, и коммит падал на `Author identity unknown`. Глобальный конфиг там прописывать не стоит — у владельца своя подпись в этом же репозитории; правильнее передавать `git -c user.name=... -c user.email=...` на каждый коммит агента.

## 20. Образ сервиса собран без пакета, который он импортирует, — а тесты зелёные

**Проблема** (найдено 25.09, ТЗ #4 И3): с И1 `analyzer/llm_client.py` зависит от `llm_core`, а `api/main.py` импортирует `analyzer.llm_client` на верхнем уровне. Но образ API (`api/Dockerfile`) копировал только `api/`, `database/`, `config/`, `analyzer/`, и в compose у сервиса не было тома `./llm_core`. API падал на старте с `ModuleNotFoundError: No module named 'llm_core'`. Тесты этого не видели: весь pytest гоняется в контейнере `analyzer`, где примонтировано всё.

**Решение**: `COPY llm_core/ /app/llm_core/` в `api/Dockerfile` и `./llm_core:/app/llm_core` в томах сервиса (`b405939`). Проверка: `docker compose run --rm --no-deps news-radar-api python -c "import api.main"`.

Общий урок: зелёные тесты в одном образе ничего не говорят о другом. Когда новый пакет становится зависимостью общего модуля, нужно пройти по **всем** сервисам, которые этот модуль импортируют, и в каждом сделать импорт-смоук своей точки входа.

## 21. Факты о прокси — это снимок на дату, а не свойство

**Проблема** (25.09): спека и STATE со слов morning-post (04.09) утверждали, что у прокси aiprimetech.io `/chat/completions` отдаёт `prompt_tokens: 0`, поэтому считать расход по нему нельзя. Живая проба 25.09 показала обратное: входные токены считаются (1964 на пустяковый запрос). А то, что владелец считал исчезнувшим, осталось: неснижаемая добавка ~1300 входных токенов на вызов (1317 на messages, 1964 на chat). Пустой ответ при `stop_reason: max_tokens` с посчитанными токенами тоже воспроизводится.

**Решение**: `python -m llm_core.probe` перед любыми расчётами и при каждой смене провайдера. Профиль заполняется по отчёту пробы (`data/llm_probe/`), а не по памяти. Незаполненное — `TODO(unverified)`, и гард в `resolve_active` не даст стартовать.

Общий урок: поведение чужого сервиса меняется без предупреждения, в обе стороны. Любое «у них так» в спеке должно нести дату и способ перепроверки. Выгрузка расходов прокси за 25.09 подтвердила: добавка **оплачивается** по полной цене входа. Для классификатора добавка в ~1300 токенов на вызов решающая: при ней классифицировать по одной статье за вызов дорого, нужен батч.

Сопутствующее: протокол `messages` требует `max_tokens` всегда, а анализатор вызывает модель «без лимита» (`-1`). Черновик пробы предлагает 1024, и этого хватает для пробы, но не для дайджеста. В профиле стоит 8192.

## 22. `respx.mock(...)` с параметрами — это отдельный роутер

**Проблема** (25.09): тест с декоратором `@respx.mock(assert_all_called=False)` регистрировал маршруты через `respx.post(...)` и падал с `RESPX: <Request ...> not mocked!`. Вызов с аргументами создаёт **новый** `MockRouter`, а `respx.post` добавляет маршрут в глобальный роутер по умолчанию, который в этот момент не активен.

**Решение**: `with respx.mock(assert_all_called=False) as router:` и `router.post(...)`. Голый `@respx.mock` без скобок и `respx.post` работают вместе, потому что оба указывают на глобальный роутер.

## 23. Прокси подмешивает свои инструменты — tool use и JSON через него ненадёжны

**Проблема** (25.09, ТЗ #4 И3 шаг 4): на aiprimetech.io `/messages` с принудительным `tool_choice` sonnet 5 вызвал инструмент `WebSearch`, которого мы не передавали; haiku 4.5 отвечал с китайской припиской («вызов инструмента сгенерирован не полностью…»). В текстовом режиме, **без единого нашего инструмента**, прокси 18 раз из 36 вернул `stop_reason: tool_use` с пустым текстом. id вызовов — `call_function_…`, не `toolu_…`. Скрытый системный промпт с инструментами объясняет и добавку ~1300 входных токенов на вызов. Тот же запрос через OpenRouter: наш инструмент, `toolu_…`, 14 входных токенов на «reply with ok».

**Решение**: классификация идёт через OpenRouter (`openrouter.messages`); в `LLMResponse.structured` принимается только вызов нашего инструмента, остальное — в `tool_calls_seen` для диагностики, дальше — разбор текста.

Общий урок: имя модели в прокси — не гарантия модели и не гарантия чистого контекста. Прежде чем мерить модели, прогнать один и тот же запрос через второй независимый провайдер и сравнить токены, id и поведение.

## 25. Анонс в RSS и Cloudflare: golden set видит не то, что размечал владелец

**Проблема** (25.09): g22 и g32 (OpenAI) владелец размечал «ценно» по полной странице, а в наборе и в проде — анонс в 150 символов. Догрузка полного текста получает 403 Cloudflare challenge (с любым User-Agent). Все модели ставят им 2 — и правы относительно того, что видят.

**Решение**: тексты не меняли; eval печатает дополнительно точность без них (`UNFETCHABLE`). Источник полного текста для openai.com — долг коллекторов. Обходить защиту от ботов нельзя.

## 26. Промпт подтянут на том же наборе, на котором меряется

**Проблема** (25.09): v2 промпта `ai_value` писался после разбора ошибок v1 на тех же 36 примерах (haiku: 80.6% → 91.7%). Правила взяты из спеки р.3.1 и комментариев владельца к разметке, а не из конкретных текстов, но отложенной выборки нет — цифра оптимистична.

**Решение**: пока — честно помечено в отчёте. Проверка — на живых дайджестах (шаг 5 / И4) и на следующем датированном наборе разметки: он становится отложенной выборкой для текущего промпта.

## 27. У моделей рассуждений свои запреты на параметры

**Проблема** (25.09): GPT-6 (luna / sol / astra) через `/chat/completions` отвергает `temperature: 0.3` (только по умолчанию), `max_tokens` (нужен `max_completion_tokens`), а function tools разрешает только при `reasoning_effort: none` — которого у astra нет вовсе. Классификатор всегда слал `temperature`, так что ни один вызов не прошёл бы.

**Решение**: поле профиля `model_params` — повадки запроса по id модели, `null` убирает ключ (`e771465`). Повадки живут в каталоге, а не в `if model == …`. Astra — в текстовом режиме с `reasoning_effort: low`.

Общий урок: «OpenAI-совместимый» — это про формат, а не про набор допустимых параметров. Новую модель сначала проверять одним запросом с теми же параметрами, что шлёт наш код, и только потом запускать замер.

## 28. Модель в листинге OpenRouter ≠ модель, которую можно померить

**Проблема** (26.09): `qwen/qwen3.8-flash` есть в `/models`, но весь прогон eval упал: единственный провайдер (Alibaba) отдавал 429 «temporarily rate-limited upstream», часть вызовов — 400. Ретраи не помогли, прогон — 36 сломанных ответов и `cost: null`. Попутно: у Qwen и DeepSeek на OpenRouter задержка батча 28–89 с против 17 с у haiku — хостинг у разных провайдеров разный. И алиасы `~vendor/…-latest` меняют модель без предупреждения — для замера только закреплённые id.

**Решение**: модель, упавшую на лимитах, считать «не измерена», а не «плохая»; перед большим прогоном — один запрос. Если такая модель пойдёт в маршрут — либо свой ключ провайдера (BYOK), либо закрепить провайдера в запросе OpenRouter.

## 29. Снятие mypy-baseline показывает не все ошибки сразу

**Проблема** (27.09): при снятии `ignore_errors` с `analyzer/analyzer.py` исполнитель (Codex) чинил ошибки, не имея mypy, по счёту «26 штук» — и починил 7. Остальные 19 (`no-untyped-def`, `type-arg`) — уровня `strict`, хотя `analyzer.py` в strict-секциях не стоит (причина не выяснена; секция `value_funnel` ни при чём — проверено).

**Решение**: список ошибок передавать исполнителю дословно (вывод mypy), а не числом. Добивал оркестратор: `dict` → `dict[str, Any]`, `-> None`, без изменения поведения.

## 30. Неизвестное значение перечисления = вечный повтор

**Проблема** (27.09): классификатор отбрасывал вердикт с `content_type` вне перечисления (g30 → `other`). В пайплайне такая статья остаётся `analyzed=0` и уходит в модель каждый цикл, за деньги.

**Решение** (владелец, 27.09): `content_type` → `opinion`, `topic` → `other` с WARNING; `value_score` остаётся настоящим. Общее правило: ошибка разбора, которая повторится на тех же данных, не должна оставлять запись в очереди.

## 31. «Короткий» не равно «анонс»; лимит догрузки навсегда оставлял тизер

**Проблема** (27.09, вопрос владельца): признак «в фиде только сниппет» реализован как «чистый текст < 500 символов». Хабр отдаёт тизеры 300–1500 символов → 13 из 13 статей Хабра в golden set — тизеры, модели классифицировали по ним, а владелец размечал по полной статье. Короткие тизеры (< 500) тоже остались тизерами: догрузка упёрлась в `max_per_feed: 5`, а запись с известным URL больше не перечитывается. Перекачка показала: все 13 страниц Хабра отдаются нормально (8–23 тыс. символов).

**Решение**: `sources.fulltext.mode = "always"` + отложенная обработка при лимите (`docs/02_collector.md`). Урок: проверять, *что именно* видит модель в проде, а не только что она ответила; и golden set должен хранить тот же текст, что пайплайн.

## 32. Один прогон eval — не замер

**Проблема** (27.09): haiku на тех же 36 примерах, том же промпте и модели: 25.09 — 91.7% и PASS, 27.09 — 86.1% и FAIL (g28 «хайп» получил 8). Разница между прогонами сопоставима с эффектом, который меряем.

**Решение**: решения по модели/промпту/тексту принимать по нескольким прогонам (минимум 3 на вариант, среднее и разброс), одиночный прогон — только смоук.

## 33. Модель `digest` в каталоге была мёртвой записью

**Проблема** (27.09): анализатор создаёт один `LLMClient` с задачей `default` и через него же пишет дайджест и называет тренды. Записи `models.digest` в профилях (opus 5 на OpenRouter) никто не читал — дайджест писал sonnet 5 (`default`). Всплыло при выборе модели на дайджест для профиля OpenAI.

**Решение**: `task=` на вызов в `LLMClient.complete*`, дайджест → `digest`, тренды → `trend_name` (тест `tests/test_llm_task_override.py`). Урок: запись в конфиге без потребителя выглядит как работающая настройка — проверять, что её кто-то читает (как с `llm_model` в И1).

## 34. Два обработчика одного URL скрывают полный конфиг

**Проблема** (И4.1, шаг 2b): `api/main.py` регистрировал `GET /settings` дважды. Первый обработчик
возвращал только три поля, поэтому бот не мог увидеть `digests`, хотя второй обработчик читал весь файл.

**Решение**: оставить один обработчик с полным конфигом; HTTP-тест проверяет наличие расписания.
Также `ConfigWatcher.get()` сам файл не перечитывает: анализатор теперь запускает `cfg.watch()` вместе
с основным циклом, иначе hot reload категорий оставался бы только обещанием.

## 35. Первая часть дайджеста может сдвинуть окно второй

**Проблема** (И4.1, шаг 2b): если каждая категория читает последний `period_end` по общему имени
после предыдущей вставки, вторая часть смотрит только новости, пришедшие за время генерации первой.

**Решение**: вычислить начало окна один раз до обхода категорий; при отметке соседей по тренду
ограничивать UPDATE источниками категории, чтобы старый смешанный тренд не поглотил другую часть.

## 36. Дайджест длиннее 4096 символов не доходит вовсе

**Проблема** (И4.1, живой прогон 28.09): шаблон `ai_value` на 8 пунктов дал 4254 видимых символа.
Бот отправлял часть одним сообщением: Telegram отвечал «Message is too long», запасная отправка
простым текстом падала так же — владелец не получал ничего. У `spoiler`/`classic` текст был короче,
поэтому баг не проявлялся.

**Решение**: `bot/digest_schedule.py::split_message` режет часть по пустым строкам между пунктами
(HTML-теги пункта не рвутся) и меряет сырую длину с тегами — это верхняя граница того, что считает
Telegram. Плюс `max_items: 7`, чтобы обычный выпуск влезал в одно сообщение.

## 37. Блокировка, которая ничего не защищает

**Проблема** (И4.1, живой прогон 28.09): при старте анализатора bge-m3 грузился трижды. В
`Embedder._load` под `with self._lock` стояла только проверка и строка лога, сама загрузка шла после
выхода из блока — три параллельных `encode()` из пула потоков проходили проверку и грузили модель
каждый сам (×3 память и время).

**Решение**: загрузка внутри блокировки (double-checked locking). Тест с медленной подменой
`SentenceTransformer` из трёх потоков — `tests/test_embeddings_hook.py`.

## 38. Chroma писала векторы не в смонтированную папку

**Проблема**: `chromadb/chroma:latest` (1.x) хранит данные в `/data`, а в compose был смонтирован
`./data/chroma:/chroma/chroma` (путь старых версий). Папка на хосте пустая, векторы жили в слое
контейнера и терялись при пересоздании. Тег `latest` сменил путь молча.

**Решение**: том `./data/chroma:/data`. Перед пересозданием контейнера скопировать живые данные:
`docker cp news-radar-chroma:/data/. data/chroma/`.

## 39. httpx пишет токен бота в лог

**Проблема**: `httpx` на INFO логирует URL каждого запроса, а Telegram Bot API держит токен в пути
(`api.telegram.org/bot<токен>/...`). Логи бота содержали токен.

**Решение**: `logging.getLogger("httpx").setLevel(logging.WARNING)` в точках входа бота, анализатора и API.

## 40. «Реклама» съедала полезные статьи вендоров

**Проблема** (И4.1, живой прогон 28.09): промпт `ai_value-v2` говорил лишь «Mark commercial promotion as
is_ad=true». gpt-6-luna пометила рекламой 30% статей RSS/HN, включая технические посты компаний о своих
продуктах с оценкой 7–8. `is_ad=1` выкидывает статью из дайджеста целиком, поэтому ошибка молча теряет
лучшие материалы. Eval проверял только ценность и `is_ad` не мерил вовсе.

**Решение**: узкое определение `is_ad` в `ai_value-v3` (реклама = цель продать и нет пользы без покупки;
самореклама снижает оценку, а не ставит флаг), датированный набор `tests/golden/ADS.md` и замер
`tests/eval_ad_flags.py`. Любое новое поле вердикта, которое отбрасывает статью, должно иметь свой замер.

## 41. Новый код в томе не работает, пока процесс не перезапущен

**Проблема** (И4.1, 28.09): код анализатора смонтирован томом (`./analyzer:/app/analyzer` и др.), поэтому
`docker exec ... python -c "import ..."` показывает свежую версию, а сам цикл анализатора держит модули,
загруженные при старте. Процесс поднят в 16:16, промпт `ai_value-v3` закоммичен в 21:13, учёт `llm_usage` —
в 20:15: цикл в 21:01 разбирал статьи по v2 (6 из 10 — «реклама»), расходы классификатора в БД не писались.
Вдобавок `docker compose --profile feeds up -d --build analyzer` пересобрал образ, но контейнер остался
прежним («Running», а не «Recreated»).

**Решение**: после правок кода анализатора/API/бота —
`docker compose --profile feeds up -d --force-recreate --no-deps <сервис>` и сверка
`docker inspect <контейнер> --format '{{.State.StartedAt}}'` с временем коммита. Проверять версию промпта
нужно по логам цикла, а не по `docker exec`.

## 42. Модель изредка ломает JSON в длинном пересказе

**Проблема** (И4.1, 29.09): для message 284 (статья Хабра на 6,5 тыс. символов) gpt-6-luna вернула пересказ
с синтаксической ошибкой JSON на ~3600-м символе (`Expecting ',' delimiter`), и заметка в `knowledge`
не создалась. Повторный вызов с тем же промптом дал валидный JSON — сбой случайный. В логе были видны
только первые 300 символов ответа, место поломки — нет. Строгий JSON-режим провайдера не включён:
флаг `supports_json_schema` в `llm_core/providers.py` объявлен, но не используется.

**Решение**: `complete_json` бросает `LLMJSONError` и логирует текст вокруг места ошибки;
`generate_doc` и нарезка длинных статей повторяют вызов один раз. Включение JSON-режима провайдера —
отдельной задачей в `llm_core`.

**Дополнение 01.10:** сбой оказался не случайным. На статье 473 (Хабр, 28 тыс. символов) — 3 сбоя подряд в
одном месте: поле `how` в схеме промпта — строка, а модель пишет несколько абзацев и закрывает их `"]`.
Повтор с тем же промптом этого не лечит. Решение — строгий режим (`llm_strict_json_tasks`, схема-инструмент
со `strict` у OpenAI): провайдер не даёт модели выйти за схему. Урок: если JSON ломается в одном и том же
месте — это расхождение схемы с тем, как модель хочет писать, а не шум.

## 43. Лимит Telegram считается по видимому тексту, а не по HTML

**Проблема** (И4.1, 29.09): выпуск `articles` пришёл двумя сообщениями, хотя видимого текста в нём 3821
символ при лимите 4096. `split_message` мерил длину вместе с тегами и адресами ссылок (5478), а у дайджеста
`ai_value` половина веса — URL разборов и статей.

**Решение**: для `parse_mode=HTML` длина считается как у Telegram — видимый текст без тегов, в единицах
UTF-16 (эмодзи = 2). Резка по-прежнему по пустым строкам между пунктами, разметка не рвётся. Аварийная
повторная отправка простым текстом (если HTML не принят) шлёт теги как текст и на пограничном выпуске
может упереться в лимит — редкий путь, оставлен как есть.

## 44. Выпуск собран, но не отправлен: сон Mac посреди генерации

**Проблема** (02.10): Mac проснулся в фоне (DarkWake) на 45 с в 09:45 МСК, планировщик бота запустил пропущенный
слот, API начал генерацию, и Mac снова уснул. В 10:21 (открыта крышка) у бота истёк тайм-аут 180 с —
`Error triggering scheduled digest:` с пустым текстом (`httpx` тайм-аут), слот считается отработанным. API через
25 с собрал и сохранил выпуск №6 (статьи помечены `in_digest=1`), но бот его уже не ждал — в Telegram ничего.

**Решение владельца**: не чинить — на сервере сна нет. Если всплывёт и там (перезапуск бота, обрыв сети), вариант —
«исходящие»: бот раз в минуту рассылает выпуски с `digests.sent_telegram = 0` и помечает их. Собранный выпуск
доступен в боте командой `/digest articles`.
